## The 504 story, start to finish

Worth reading once, because the surface symptom lied twice.

1. `judge=llm` returned **504 at 15.1s** in production for weeks. The queued fix
   was an nginx `proxy-read-timeout` annotation.
2. That fix would never have worked. welance-charts **!143** established why: on
   the `gatewayApi` path the nginx `proxy-*-timeout` annotations are **inert**,
   so every tenant on Gateway API silently fell back to **Envoy's 15s default**.
   The chart gained an opt-in `ingresses.web.timeouts`, and the tenant MRs
   (welance-prod !13, welance-noprod !29 and !31) set `request: 300s`.
   **All three environments now carry it** — verify with:
   `kubectl get httproute -n r001-15-production -o yaml | grep -A3 timeouts:`
3. Removing the 15s cut exposed what it had been hiding. The judge ran to
   completion and *still* failed, now at **502**:
   `JSONDecodeError: Unterminated string starting at: line 62 column 14 (char 1569)`.
   `PB_LLM_MAX_TOKENS` was **1500**, which does not hold fourteen verdicts each
   carrying a verbatim quote. Never a timeout — a ceiling.
4. Fixed in **1.9.1/1.9.2**: ceiling at 4000, pinned to the rule count by
   `tests/test_truncated_judge.py`; truncation is now a named condition
   (`JudgeTruncated` from the provider's `finish_reason`/`stop_reason`,
   `JudgeUnparsable` when the array just stops) returning **503 that names the
   ceiling**, on `/v1/score` and both suggest endpoints.

**A partial answer is never scored.** Missing verdicts default to
`not_applicable`, which silently *changes the number*. A refusal beats a wrong
score. Do not "salvage" a truncated array.

## Two dead ends — do not re-derive these

Both were reasoned, deployed to develop, measured, and disproved.

| hypothesis | test | result |
|---|---|---|
| a bigger ceiling gives a reasoning model more room | 4000 vs 8000 vs 16000 in production and develop | identical behaviour; ceiling is not the variable |
| `reasoning: {effort: "low"}` cuts latency | deployed to develop, three runs | no improvement; the knob shipped **off** |

`PB_LLM_REASONING_EFFORT` survives as a knob defaulting to empty — it sends no
reasoning field at all. It exists because the next model may want one.

## The one thing still open

**Something in front of `briefs.welance.com` hangs up at ~50.1s**, while the
route grants 300s and the pod logs the model answering `200 OK` at that same
moment. Measured repeatedly to within 200ms. It is *not* Envoy's default and
*not* the HTTPRoute; both are accounted for. Noprod hosts (`*.welance.space`)
survived 46–49s answers, so suspicion falls on the shared prod entrypoint or
the Cloudflare record fronting the welance.com zone. Ask Amedeo.

This matters because judge latency wanders with the provider, and the two
straddle each other:

```
2026-08-20 evening   25.1s  15.8s  25.4s  30.8s   → all 200
2026-08-21           50.2s  42.0s  40.7s  43.8s   → one 520, three 200
```

So production is **intermittent**, and the only difference between the failure
and the successes is that the judge took 50s instead of 42s.

Two independent fixes, both worth doing:

1. Identify and raise the ~50s layer (platform; the evidence above is enough to
   open the conversation).
2. Make the judge faster so the ceiling stops mattering. One call currently asks
   one model to judge all fourteen rules in sequence. The rules are independent
   and **the seam already forbids the model touching any number**, so concurrent
   batches (e.g. three calls of five rules, merged before `aggregate`) should cut
   wall-clock roughly threefold. This is a real change to `app/scorer.py` with
   fixture implications — it is a decision, not a slip-in.
