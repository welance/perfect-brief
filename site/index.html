what it does

A score

0 to 100, a weighted average over fourteen public rules. Problem, users, outcome, scope, budget, deadline.

A gate

Four hard requirements. Fail one and the brief is blocked, whatever the score. A brilliant brief that names the client stays off a blind noticeboard.

Evidence

Every verdict quotes the brief. The model only judges; code owns every number, so the same brief and the same version always agree.

Two rules, anonymisation and the €10k floor, are noticeboard policy, not virtues. They carry context: directory; send gate_contexts: [] to score a generic brief without them.

How it works

Software is cheap to build now and easy to build wrong. The brief is the one part you can still get right before anyone, human or model, starts. 20% brief, 80% team: fourteen open rules check the 20%.

One seam. The rules are versioned YAML files anyone can read and anyone can change. A model reads one rule at a time and answers pass, partial or fail, with a quote. Past the seam, code does the arithmetic.

the fine print

The judge runs at temperature zero, but model output is not promised to be deterministic across provider updates. Service-funded verdicts are cached by ruleset version, model and brief; bring-your-own-key calls are always fresh. A score exists only when the judge returns all fourteen valid verdicts, each with evidence copied verbatim from the brief. A corpus of labelled examples runs in CI: a rule change that moves the numbers has to move those fixtures too.

welance runs authoritative publish scoring on DeepSeek V4 Pro. Suggestions and their verifier run on DeepSeek V4 Flash. The model names are returned by the API; Sonnet is not enabled on welance deployments.

Why we built it, honestly

We are welance, a collective of independent senior teams since 2011. We run welance/Directory, a blind noticeboard where teams pick up briefs on the strength of the brief, not the brand. Its guided builder asks these fourteen questions and scores every draft with this service.

One company running both the noticeboard and the bar is a conflict. Our answer is to make the bar open: public rules, public weights, a public test corpus, MIT. Disagree? Fork it.

welance also pitches as a team on the Directory. Same fees, same blindness, same bar; the version on every verdict is how anyone checks. What binds us is the Operator Covenant: never mining briefs for leads, never training on them.

the fine print

This tool is the distilled version of what fifteen years of handoffs taught us: the products that go well aren't the ones with the most polished decks — they're the ones where a small, senior, cross-functional team got a brief honest enough to start from. We can't open-source the teams. We can open-source the bar.

Together, this service and the Directory are the digitalised version of what welance has always done in person — matching honest briefs with senior teams — rebuilt with the approaches we now believe in: open rules instead of opinions, inspectable scores instead of gut feel. Two convictions drive it. Writing a good technical brief for a software product should be easy — the bar should help you clear it, not just measure you. And no one should have to commit to the first team they meet: a brief worth building deserves to meet several, so the fit — technical and cultural — is chosen, not defaulted to.
