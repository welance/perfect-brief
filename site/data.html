Your brief, your key_

A project that asks you to trust an open bar owes you the boring details: what leaves your machine, what we keep, for how long, and what we never keep at all.

what travels where
what where it goes what we keep
The brief text To our service, then through OpenRouter to the DeepSeek provider that judges it. The API receives the assembled text, not original files. never stored as a document — only its verdict survives, one row down, for a day
The verdicts Back to you. Each carries a short quote copied verbatim from your brief as evidence. cached 24h — keyed by a hash of the brief, so the same brief is not re-judged and re-charged. This holds even when you bring your own key: the cache is shared, so an identical brief may be answered from it rather than charged again. Send no_cache: true and nothing is read or written.
Your model key Forwarded once, over TLS, to the provider — as the Authorization header of that single call. never stored, never logged, never part of any cache key
Who you are Nowhere. No accounts, no cookies, no analytics. The pages fetch fonts (welance.com, Google's Noto for non-Latin scripts) and nothing else — a test fails if any page reaches any other host. one per-IP rate counter in Redis, expiring with its window — nothing else

The cache exists for one reason: the judge is deterministic at temperature 0, so scoring the same brief twice should cost once and answer identically. Honestly stated, that means fragments of your brief do survive for a day: each cached verdict carries its short verbatim quote, keyed by a hash of the full text. Never the document itself, never past 24 hours — and no_cache: true skips it entirely.

what binds us — the operator covenant

The rules on this site judge briefs. The Operator Covenant judges us — it exists because welance runs the Directory this bar gates and pitches on it as a team. In short: we never mine briefs for leads, never train on them, never contact anyone because of what a scored brief contained, and our own briefs pass the same gate, same model, same version.

Where code can enforce a promise, it does: the key-leak canary already fails the build if a key ever reaches a log, a cache, or a response, and the same treatment for brief bodies is next. Where code can't reach — we do run the servers — the covenant names the limit plainly instead of hiding it, and self-hosting remains the exit that needs no trust at all.

bring your own key

With your key, we run no model for you.

Send an OpenRouter key in the x-llm-key header and the judgement runs on your account. welance still restricts that path to DeepSeek V4 Pro or Flash, so an internal proxy cannot accidentally select Sonnet. We forward the call and hand you the result — no service-funded model is invoked, nothing about the key is retained, and BYOK scoring bypasses the shared verdict cache.

bash · your own judge
curl -X POST https://briefs.welance.com/v1/score \
  -H 'content-type: application/json' \
  -H 'x-llm-key: sk-or-…' \
  -d '{"brief":"…","judge":"llm","model":"deepseek/deepseek-v4-pro","no_cache":true}'

The MCP server reads the same key from PB_LLM_KEY, so an assistant on your machine can score briefs entirely on your own account.

Handing your key to somebody else's server deserves more than our word for it. Every line of ours that touches it — and the test that fails if that ever changes — is written out on its own page.

if that is not enough

Some briefs cannot leave a perimeter, and some organisations need a data-processing agreement, a named model, or the whole thing running somewhere else. That is a conversation, not a checkbox: write to hello@welance.com and we will tell you plainly what is possible — including running it on models we select, or handing you the deployment to run yourself. It is MIT-licensed; self-hosting is a right, not a favour.

the honest limits

We do not control OpenRouter or its routed provider's retention; their terms apply once a brief leaves this service. The API receives text only, not original document bytes or attachments. It is rate-limited and served over TLS, but it is a small open-source service, not a compliance product. For genuinely confidential material, use a spend-capped key or run your own copy.
